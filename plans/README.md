## Direction findings (maintainer decisions, not defects)

1. **Wallet re-enablement is one decision away, not one project away.** Full implementations exist (`lib/passes/apple.ts`, `lib/passes/google.ts`, both API routes); UI shows "Próximamente". The work left is operational (Apple cert, Google issuer account), a feature flag (env var or `Business` boolean), and the route hardening listed above. Roadmap already gestures at this; a short design/spike plan would settle the flag strategy.
2. **Operational tooling lags the data model**: deletes are one-at-a-time with per-record confirmation; no bulk archive of cards/customers after a promotion ends. Evidence: soft-delete flags exist on both models, customers table just gained sort/filter, but no batch endpoints. Worth a product call once real merchants ask.
3. **An API surface already half-exists**: there's an OpenAPI route (`app/api/openapi`) documenting the REST endpoints. If Koda POS integration is the goal (README: "Parte del ecosistema Koda POS"), token-based API auth for machine clients is the natural next step; today everything assumes cookie sessions.
