## Identificación

- Commit observado: `9cd409448fb58e544a61b6ca9be0207922f89b57`.
- Versión de `package.json`: `1.2.0`.
- Estado de release: `1.2.0` está en desarrollo; este documento no afirma que

- Propósito: conservar el comportamiento y los límites de la base desde la que
  se escribirán las especificaciones de la siguiente versión.

## Producto y actores

Koda Fidelity permite que pequeños negocios creen tarjetas digitales de
lealtad. El negocio configura una tarjeta y comparte un QR o enlace; su equipo
opera sellos y canjes desde el dashboard. Los clientes se inscriben y consultan
su progreso desde el portal web.

Los actores presentes en el modelo son administradores y selladores del
negocio, además de clientes con perfil autenticado. Los roles de negocio son
`admin` y `sellador` (`prisma/schema.prisma`). Las rutas API resuelven el
negocio desde la sesión y aplican autorización por rol en el servidor
(`lib/api-utils.ts`).

## Capacidades observadas

- Alta y recuperación de cuentas, callbacks de autenticación, onboarding con
  borrador recuperable y provisioning posterior a la confirmación
  (`app/auth/`, `app/onboarding/`, `lib/onboarding-service.ts`,
  `lib/signup-provisioning.ts`).
- Administración de negocio, tarjetas, marca, clientes y colaboradores en el
  dashboard (`app/dashboard/`, `app/api/`).
- Registro de sellos y canjes con operación idempotente y persistida como
  ledger (`lib/loyalty-engine.ts`, `prisma/schema.prisma`).
- Planes Lite/Pro, solicitudes de activación y tareas de ciclo de suscripción;
  el repositorio incluye activación manual y no demuestra procesamiento de
  cobros (`lib/account-lifecycle.ts`, `app/api/subscription-requests/`).
- Cierre de cuenta de negocio con ejecución y tareas de limpieza de recursos
  (`app/api/account/`, `app/api/business/closure/`,
  `app/api/cron/account-closures/`).
- Rutas de pases Apple y Google existen, pero la línea de conocimiento de
  Fidelity indica que Wallet queda deshabilitado por feature flag y es
  candidato a 1.3.0; tener rutas no significa que la capacidad esté disponible.

## Arquitectura observada

| Parte | Responsabilidad y ubicación |
| --- | --- |
| Aplicación web | Next.js App Router; páginas y layouts en `app/`, UI reutilizable en `components/`. |
| API | Route Handlers en `app/api/`; las operaciones de negocio obtienen su principal de sesión y validan acceso al tenant. |
| Identidad | Supabase Auth y sesiones SSR mediante `@supabase/ssr`; la identidad interna de negocio se vincula con `User.authUserId`. |
| Persistencia | PostgreSQL administrado por Supabase, accedido desde el servidor mediante Prisma; `prisma/schema.prisma` y `prisma/migrations/` son el contrato de datos del repositorio. |
| Archivos | Supabase Storage para assets privados/públicos de negocio y perfil, según las rutas y utilidades correspondientes. |
| Operación | Scripts en `scripts/`, cron handlers en `app/api/cron/`, y despliegue/CI en `.github/workflows/`. |
| Verificación | Vitest para unidad, componentes e integración; Playwright para recorridos E2E; CI incluye generación de Prisma, lint, typecheck y tests. |

Prisma es el acceso de aplicación a PostgreSQL; no sustituye a Supabase Auth ni
implica que la autorización de tenant dependa de RLS. Las especificaciones que
modifiquen acceso a filas o archivos deben documentar por separado el principal,
el tenant, el rol y el mecanismo de acceso efectivo.

## Reglas e invariantes presentes

- Las escrituras y lecturas privadas se limitan al `businessId` resuelto desde
  la sesión autenticada; no se confía en un tenant enviado por el navegador.
- Los roles de negocio son `admin` y `sellador`; la API aplica las capacidades
  administrativas en el servidor.
- Una operación de lealtad incluye negocio, cliente, tipo e idempotency key; el
  ledger conserva el resultado para responder reintentos sin repetir el efecto
  (`lib/loyalty-engine.ts`).
- El progreso del onboarding tiene versión de borrador y estado persistido,
  para detectar y reanudar el flujo (`OnboardingProgress`).
- Los cambios de esquema se representan mediante migraciones versionadas. Una
  especificación que cambie datos debe considerar tanto el schema como el orden
  de migración desde una base vacía y desde bases existentes.
- Los pases Wallet no deben considerarse una capacidad liberada mientras siga
  vigente el gate documentado en el contexto compartido de Fidelity.

## Fuera de esta línea base

- No se ha confirmado que cobros recurrentes o facturación estén implementados.
- No se afirma que Apple Wallet o Google Wallet estén habilitados para usuarios.
- La existencia de una pantalla, endpoint, prueba o modelo no demuestra por sí
  sola que una capacidad cumpla todos los criterios de release.
- El roadmap o el plan de diseño compartido no quedan convertidos
  automáticamente en alcance aprobado de `1.3.0`.

mantener esas áreas como propuestas o incógnitas, sin asignarles una misión,
prioridad o fecha que no esté documentada.
